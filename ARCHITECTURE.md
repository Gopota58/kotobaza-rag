# Архитектура

Документ описывает, **как разложен код и кто за что отвечает**. Обоснование решений —
в [`DECISIONS.md`](DECISIONS.md).

## Слои

```
transport (тонкие клиенты)        core (переиспользуемое ядро)        infra (внешний мир)
───────────────────────────       ──────────────────────────────      ─────────────────────
app.py        FastAPI HTTP   ┐                                        Chroma (chroma_db/)
bot.py        Telegram       ├──►  rag/engine.py  RAGEngine      ──►  Embeddings (API | MiniLM)
desktop_client.py  Tkinter   ┘      ├ build_embeddings()              LLM server (LM Studio/Ollama/OpenAI)
                                    ├ build_llm()                     Telegram API (через прокси)
static/index.html  веб-чат          ├ retriever (гибрид + RRF)
                                    ├ ask() / reindex()
                                    └ watcher (поток: watchfiles + filelock)
```

- **`rag/engine.py` — единственное место, где живёт тяжёлое состояние** (Chroma-коллекция,
  эмбеддинги, LLM-цепочка). Всё остальное — обёртки.
- **`config.py`** — типизированные настройки из `.env` (`pydantic-settings`). Ни один
  модуль не читает `os.environ` напрямую и не содержит хардкодных путей/секретов.

## Модель процессов и «единый владелец индекса»

Запускается до трёх процессов:

1. **Веб-сервер** (`uvicorn app:app`) — **владеет** `RAGEngine` и **единственный** запускает
   фоновый `watcher` переиндексации. Все мутации индекса идут через него.
2. **Telegram-бот** (`bot.py`) — **тонкий HTTP-клиент**: не открывает Chroma и не дёргает
   LLM напрямую, а шлёт `POST /ask` / `POST /ingest` на веб-сервер.
3. **Десктоп/браузер** — тоже клиенты к HTTP-API.

Зачем: Chroma + эмбеддинги — дорогое и неконкурентное состояние. Если бы его держал
каждый процесс, переиндексация из бота рассинхронизировала бы индекс веб-сервера. Единый
владелец убирает эту гонку. Межпроцессную корректность на случай параллельных вызовов
`reindex()` довершает **`FileLock`** (`chroma_db/.reindex.lock`) плюс **сигнатура** набора
файлов (`chroma_db/.docs_sig`) — пересборка пропускается, если содержимое не менялось.

## Жизненный цикл запроса (`ask`)

1. `retriever.get_relevant_documents(q)` — векторный cosine (нормализованные векторы)
   **и** BM25/TF-IDF по корпусу; ранги сливаются через **Reciprocal Rank Fusion**, топ-`k`.
2. Сборка контекста с ограничением `LLM_MAX_CONTEXT_CHARS` (защита окна модели).
3. Промпт (`SYSTEM_INSTRUCTION` + контекст + вопрос; system-роль опциональна) → LLM.
4. Парсинг `content`. Пустой `content` (типично для reasoning-моделей) → явная ошибка,
   а не тихий пустой ответ.

## Жизненный цикл переиндексации (`reindex`)

`docs/*.txt` → `AutoDetectTextLoader` (`chardet` определяет кодировку) →
`RecursiveCharacterTextSplitter` (400/60) → эмбеддинги (API или локальные) →
`Chroma.from_documents`. Пересоздаётся **только коллекция** через общий
`PersistentClient`, после чего `retriever`/`rag_chain` переподключаются на лету —
папка `chroma_db/` не удаляется (нет блокировок файлов на Windows).

## Наблюдаемость и отказоустойчивость

- Логи приложения — `logging`; логи watcher'а — `logs/watcher.log`.
- `bot.run_supervised()` — супервизор: перехватывает падение `polling`, ждёт и
  перезапускает; `bootstrap_retries` даёт веб-серверу время подняться перед стартом бота.
- Все внешние вызовы (LLM, embeddings, Telegram) идут через `httpx` с явным
  `trust_env` — локальные endpoint'ы не пускаются через системный прокси (см. ADR-004).

## Тестуемость

Ядро изолировано от транспорта, поэтому `ask()` проверяется со **стаббингованной LLM**
(`tests/test_ask_mock.py`) — весь CI-сьют зелёный без GPU и без запущенного LLM-сервера.
Retrieval и переиндексация — отдельными тестами на реальном Chroma (временная директория).
