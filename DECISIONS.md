# Architectural Decision Records

Короткие записи «проблема → решение → чем заплатили». Формат вольный ADR.

## ADR-001. Гибридный ретривер (вектор + BM25/TF-IDF) вместо чистого cosine
- **Контекст.** Корпус — короткие факты на русском; маленькие эмбеддинги плохо ловят
  точные ключевые слова (названия пород, инструментов), а чистый BM25 — синонимы.
- **Решение.** Два ретривера, слияние рангов через **Reciprocal Rank Fusion** (`k=6`).
- **Плата.** Двойной поиск, чуть выше задержка. RRF не требует подгонки весов — устойчиво.

## ADR-002. Единый владелец индекса (веб-сервер), бот/десктоп — HTTP-клиенты
- **Контекст.** Chroma + эмбеддинги — дорогое неконкурентное состояние; несколько
  процессов, открывающих одну коллекцию, гонят друг друга при переиндексации.
- **Решение.** Индекс и LLM-цепочку держит только `app.py`. `bot.py` и десктоп шлют
  `POST /ask`/`/ingest`. Фоновый watcher — тоже только в веб-сервере.
- **Плата.** Бот зависит от доступности веб-сервера (решено супервизором с ретраями).

## ADR-003. Переиндексация без `rm -rf chroma_db`
- **Контекст.** На Windows удаление папки, открытой PersistentClient, блокируется;
  рассинхрон живой цепочки даёт «окно», когда запрос падает.
- **Решение.** Пересоздаётся только коллекция через общий `PersistentClient`, затем
  `retriever`/`rag_chain` переподключаются. Межпроцесс — под `FileLock`; лишний прогон
  отсекает сигнатура файлов.
- **Плата.** Чуть сложнее код reindex; зато нет блокировок и «мёртвых окон».

## ADR-004. Telegram через HTTP-прокси + `trust_env=False` (обход блокировки в РФ)
- **Контекст.** `api.telegram.org` блокируется на уровне сетей → прямой запрос в таймаут.
- **Решение.** `HTTPXRequest(proxy=TELEGRAM_PROXY, httpx_kwargs={"trust_env": False})`.
  Проксируется **только** Telegram; локальные вызовы к RAG идут напрямую.
- **Плата.** Нужен внешний прокси/VPN. `trust_env=False` критичен: иначе httpx пустит
  localhost через системный `HTTP(S)_PROXY` и всё сломается.

## ADR-005. Требование не-reasoning модели + явная ошибка на пустом `content`
- **Контекст.** Reasoning-модели (Qwen3-thinking и пр.) кладут ответ в
  `reasoning_content`, оставляя `content` пустым → RAG «молчит».
- **Решение.** В доках — требование instruct-модели; опция `LLM_EXTRA_BODY` для
  `enable_thinking:false`; при пустом `content` движок бросает понятную ошибку.
- **Плата.** Ограничение на выбор модели. Зато отказ явный и диагностируемый.

## ADR-006. Сменные эмбеддинги: локальные MiniLM или OpenAI-совместимый API
- **Контекст.** Локальный `all-MiniLM-L6-v2` слаб по-русски; мультилингвальный
  `nomic-embed-text` через LM Studio заметно лучше.
- **Решение.** `EMBED_PROVIDER=local|api`; импорт `HuggingFaceEmbeddings` **ленивый**
  (внутри ветки `local`), чтобы в API-режиме не тянуть тяжёлый стек.
- **Плата.** Два пути конфигурации; локальный режим требует `sentence-transformers`.

## ADR-007. In-house метрики вместо библиотеки `ragas`
- **Контекст.** Актуальный `ragas` тянет `langchain_community...vertexai`, которого нет
  в закреплённом стеке LangChain 1.x → конфликт зависимостей.
- **Решение.** Метрики (faithfulness / answer relevancy / context precision / recall)
  реализованы поверх тех же LLM/эмбеддингов проекта.
- **Плата.** Самостоятельная поддержка; зато офлайн, без хрупких зависимостей, прозрачно.

## ADR-008. Облегчение venv: torch/transformers вынесены из дефолтного пути
- **Контекст.** `torch` (~500 МБ) грузился на старте даже в API-режиме эмбеддингов.
- **Решение.** Ленивый импорт локальных эмбеддингов (ADR-006) + удаление неиспользуемого
  ML-стека из окружения. Импорты langchain, ссылающиеся на transformers, защищены
  `try/except ImportError`, поэтому удаление безопасно.
- **Плата.** Локальный режим эмбеддингов требует переустановки стека (нужен интернет).
